# 읽기 문서 작성 기준

Easy Review의 목표는 diff를 짧게 만드는 것이 아니라, 처음 보는 사람이 변경의 목적과 흐름을 다시 조립하지 않아도 되게 하는 것이다.

리뷰는 선택이다. 원본 diff는 모두 보존하지만 읽기 화면은 중요도를 판단해 일부만 보여준다. 모든 파일과 줄을 같은 무게로 노출하면 실패한 문서다.

## 완성 기준

다음 질문에 위에서 아래로 답할 수 있어야 한다.

- 최종적으로 누구에게 어떤 동작이 달라지는가?
- 그 동작은 어디서 시작해 어떤 판단과 효과로 이어지는가?
- 저장 방식, 외부 연동, 호환성 경계가 있다면 어디인가?
- 테스트는 어떤 조건과 결과를 보증하는가?
- 지금 먼저 고치거나 확인해야 할 점은 무엇인가?

파일 목록만 읽고 독자가 흐름을 추론해야 한다면 실패한 문서다.

## 의미 묶음과 순서

한 section은 하나의 독자 질문 또는 연결된 인과 흐름을 설명한다. 같은 흐름을 구현하는 API, 서비스, 클라이언트 파일은 경로가 멀어도 함께 묶을 수 있다. 반대로 같은 디렉터리여도 서로 다른 행동이면 나눈다.

기본 읽기 순서는 다음 방향을 따른다.

- 사용자나 호출자가 만나는 진입점과 최종 결과
- 결과를 결정하는 핵심 조건과 변환
- 서버·클라이언트·외부 서비스 사이의 연동 경계
- 저장 구조, migration, 설정 같은 지원 변경
- 테스트가 보증하는 시나리오
- 생성 파일, fixture, snapshot, lockfile 같은 파생 변경

이는 고정된 카테고리가 아니다. 실제 변경에서 인과관계를 가장 잘 설명하는 순서를 고른다. 배열 순서는 Git 경로나 diff 등장 순서가 아니라 독자의 읽는 순서다.

## 파일 표시 수준

모든 파일을 읽은 뒤 다음 중 하나를 선택한다.

- `detail`: 독자가 실제 조건, 변환, 효과 또는 문제를 코드로 확인해야 한다.
- `summary`: 변경의 존재와 역할은 알아야 하지만 코드 자체가 새로운 판단을 제공하지 않는다. 화면에서는 핵심 코드 뒤의 닫힌 보조 변경 묶음으로 내려간다.
- `omitted_files`: 다른 source-of-truth에서 파생됐거나, 반복·배선·잠금 결과라 문서에서 제거해도 흐름과 위험 판단이 유지된다.

큰 diff는 상세 파일 8개 이내를 기본 목표로 삼는다. 테스트도 모두 보여주지 말고 서로 다른 계약을 대표하는 시나리오만 상세로 남긴다. 생략은 미검토가 아니다. 파일을 읽고 영향이 낮다고 판단한 경우에만 생략하며, 읽지 못한 파일은 `unreviewed_file_ids`로 분리한다.

## 문장과 제목

독자에게 내부 검토 용어를 떠넘기지 않는다.

- 나쁜 제목: `Notification service 변경`, `Mechanical`, `기타 수정`
- 좋은 제목: `알림을 받을 기기를 어떻게 고르는가`, `앱 버전을 저장할 자리를 추가한다`
- 나쁜 설명: `observed high finding`, `generated로 분류`
- 좋은 설명: `최신 기기 하나를 고르지만 실제 발송에는 회원의 모든 토큰을 넘긴다`

약어와 전문 용어는 처음 등장할 때 풀어 쓴다. 제목은 짧게, summary는 입력 → 판단 → 결과가 드러나는 1~3문장으로 쓴다. 코드 해설은 `핵심 로직`, `정책`, `연결부`처럼 이름만 붙이지 말고 그 코드가 어떤 조건에서 무엇을 바꾸는지 완전한 문장으로 설명한다.

## 먼저 볼 점

`attention`은 독자가 상세 변경보다 먼저 판단할 가치가 있는 항목만 담는다.

- `fix`: 현재 코드에서 재현 가능한 결함이나 깨진 계약
- `caution`: 조건과 영향이 구체적인 회귀·호환성·운영 위험
- `confirm`: 빠진 근거 때문에 결론이 달라질 수 있는 질문

각 항목은 발생 조건, 코드가 하는 일, 그 결과의 순서로 쓴다. 취향, 스타일, 막연한 가능성은 넣지 않는다. 해당 사항이 없으면 `먼저 볼 점` 자체를 생략한다.

## 남길 코드와 접을 코드

다음은 설명과 직접 연결되는 근거로 남긴다.

- 바뀐 계약이나 정의
- 동작 여부를 가르는 조건
- 데이터나 상태의 변환
- 반환, 저장, 요청, 이벤트, 오류처럼 관찰 가능한 효과
- 인증, migration, 동시성, 생명주기, 호환성 경계
- 테스트의 구별되는 입력과 결정적인 기대 결과

다음은 전체 내용을 복구할 수 있을 때 파일 내부에서 접는다.

- 조건과 효과가 같은 반복 호출부
- 손으로 쓴 원본 변경이 별도로 확인되는 생성 결과
- 큰 literal, fixture 준비, assertion 반복, snapshot, lockfile
- 의미가 같은 오류 문자열 조립이나 형식 변경
- 새 의미가 없는 import 정렬·추가와 dependency injection 배선

import는 자동으로 잡음이 아니다. 새 의존성, side effect, alias 변경, 새로운 아키텍처 경계를 드러내면 남긴다. 그 외 import 묶음은 `collapse`로 접고 어떤 동작에 쓰는 모듈인지 한 줄로 요약한다. `import 추가`, `dependency injection 주입`, `hook 연결`처럼 구현 행위를 그대로 옮긴 문구는 피한다. 이동 후보는 삭제와 추가를 따로 설명하지 말고 어디로 옮겼으며 주변 동작이 달라졌는지 확인한다.

마이그레이션·테스트·생성물은 보통 별도 section으로 묶고 접어 둔다. 다만 핵심 계약을 이해하는 데 필요하면 펼쳐 둔다. 접힘은 중요하지 않다는 뜻이 아니라 첫 독해에서 뒤로 미룬다는 뜻이다.

## 큰 diff

전체 파일 목록과 전역 힌트를 먼저 읽고, 파일·hunk 경계로 나뉜 모든 chunk를 검사한다. 중복이나 생성 후보는 정적 힌트일 뿐 결론이 아니다. 각 위치의 guard, 데이터 원천, side effect, 호환성 경계, 테스트 결과가 같은지 확인한다.

모든 chunk를 본 뒤 파일을 의미 묶음으로 재배열한다. 한 chunk씩 요약한 결과를 이어 붙이거나 파일 순서대로 section을 만들지 않는다. context 한계 때문에 일부만 읽었다면 미검토 파일을 명시하고 `partial`로 끝낸다.

## 근거와 검증

내부 `D...` ID는 원본 줄을 잃지 않기 위한 좌표다. 독자 화면에서는 파일 경로와 실제 old/new 줄 번호를 우선한다. 파란 강조선은 section 설명과 직접 연결된 줄에만 사용하고, 그 이유를 해당 영역 바로 위의 짧은 주석으로 보여준다.

정적 코드 확인, 로컬 테스트·typecheck·lint·build, 원격 CI, merge·배포, 실제 런타임 관측을 구분한다. 실제로 확인한 것만 기록한다. diff에 테스트 파일이 있다는 사실은 테스트 통과가 아니다.

검증 근거는 대상 코드에 관한 사실만 독자에게 보여준다. Easy Review가 모든 chunk를 열었다는 기록, 원본 hash와 계획 schema 확인, 근거 ID 유효성, coverage 계산, 렌더링 성공은 결과물의 내부 무결성 조건이지 대상 코드의 품질 근거가 아니다. 이런 자체 점검은 `verification`에 넣지 않고 실패하면 결과 생성을 중단한다.
