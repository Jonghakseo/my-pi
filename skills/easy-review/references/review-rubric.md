# 읽기 문서 작성 기준

Easy Review의 기본 독자는 프로젝트·업무 용어·시스템 구조·선행 PR·이전 대화를 전혀 모른다. 개발 경험은 있어도 이 변경의 배경은 없다고 가정한다. 일반 프로그래밍 입문 강의를 붙이라는 뜻이 아니라, 이 변경을 이해하는 데 필요한 맥락을 문서 안에서 완결하라는 뜻이다.

목표는 diff의 쉬운 번역이 아니다. 독자가 코드 없이도 문제와 해결 방식, 변경 전후의 차이, 실패의 영향을 설명할 수 있게 한다. 추상화 레벨을 높인다는 것은 ‘시스템을 개선한다’처럼 모호하게 쓰는 것이 아니라, 함수·상태값 나열을 사용자 행동과 시스템 책임의 인과관계로 바꾸는 것이다.

리뷰는 선택이다. 원본 diff는 모두 보존하지만 읽기 화면은 설명과 필요한 근거만 남긴다. 모든 파일과 줄을 같은 무게로 노출하거나 글을 이해하려면 코드를 먼저 읽어야 한다면 실패한 문서다.

## 완성 기준

코드나 이전 PR을 열지 않고 다음 질문에 답할 수 있어야 한다.

- 누가 무엇을 하려는가? 그 과정에서 지금 무엇이 부족한가?
- 이 문서의 핵심 대상은 무엇인가? 비슷해 보이는 두 개념은 어떻게 다른가?
- 변경 전과 후에 사용자·운영 담당자의 일이 어떻게 달라지는가? 그대로인 것은 무엇인가?
- 어느 시스템이 어떤 일을 맡고, 어떤 순서로 요청·결과를 주고받는가?
- 어디까지 자동으로 처리하고 어디서 사람이 개입해야 하는가?
- 문제가 발생하면 누구에게 어떤 잘못된 결과가 생기는가?
- 테스트로 확인한 것과 아직 확인하지 못한 것은 무엇인가?

필요한 배경은 PR 설명·관련 문서·정확한 버전의 코드에서 확인한다. 사업적 동기나 기존 동작을 확인하지 못했다면 미확인으로 남긴다. 선행 PR은 ‘이미 마련된 기능’과 ‘이번에 붙이는 기능’으로 먼저 설명하고, 번호·SHA는 출처나 검증 영역으로 보낸다.

## 설명의 추상화 레벨

설명은 세 층으로 쓴다. 앞층을 뒷층의 용어로 설명하지 않는다.

1. **문제와 결과**: 사용자 목적, 기존 한계, 변경 후 결과, 바뀌지 않는 범위. summary와 overview가 맡는다.
2. **역할과 흐름**: 각 시스템이 무엇을 맡고 왜 나뉘는지, 정상 처리와 실패 처리의 연결. section 제목과 summary가 맡는다.
3. **구현 근거**: 조건·상태·함수·저장 방식과 테스트. file note, focus, 접힌 코드가 맡는다.

서로 혼동하기 쉬운 개념은 먼저 역할과 차이를 설명한다. 예를 들어 ‘서버에 데이터가 저장되는 것’과 ‘화면에 저장 완료가 표시되는 것’은 별개다. 그다음 ‘서버가 저장을 마치고 응답하면 화면이 완료를 알린다’고 흐름을 연결한다. 함수명과 상태값은 그 뒤 근거를 읽을 때 소개한다. 예시는 설명 방식만 참고하고, 실제 문서에는 대상 변경에서 확인한 개념과 흐름을 쓴다.

- 도입부에 클래스명·함수명·상태 enum·SHA·파일 수를 몰아넣지 않는다.
- 어려운 용어는 단어만 번역하지 말고 목적을 설명한다. ‘멱등성’보다 ‘같은 저장 요청을 다시 보내도 데이터가 중복으로 생기지 않는다’가 먼저다.
- 설명에 필요한 용어는 최초 사용 전에 정의한다. 긴 용어집을 선행 학습으로 요구하지 말고 해당 흐름에서 짧게 소개한다.
- 정상 흐름을 하나의 구체적인 사례로 따라간다. 위험 설명에 수량·금액 예시를 쓰면 실제 정책 수치가 아닌 설명용 가정임을 구분한다.
- 파일명과 식별자를 가렸을 때도 설명의 뜻이 남아야 한다. 단, 추적 가능한 코드 근거는 없애지 않는다.

## 의미 묶음과 순서

한 section은 하나의 독자 질문 또는 연결된 인과 흐름을 설명한다. 같은 흐름을 구현하는 API, 서비스, 클라이언트 파일은 경로가 멀어도 함께 묶을 수 있다. 반대로 같은 디렉터리여도 서로 다른 행동이면 나눈다.

기본 읽기 순서는 다음 방향을 따른다.

- 사용자 목적과 기존 한계, 이번 변경으로 생기는 결과
- 필요한 개념과 등장 시스템의 역할
- 하나의 정상 사례가 시작부터 결과까지 이어지는 흐름
- 재실행·실패·취소 시 지켜야 할 약속과 자동 처리의 한계
- 운영 시작 조건과 기존 기능에 영향을 주는 경계
- 테스트와 구현 근거, 저장·설정·파생 변경

이는 고정된 카테고리가 아니다. 실제 변경에서 인과관계를 가장 잘 설명하는 순서를 고른다. 배열 순서는 Git 경로나 diff 등장 순서가 아니라 독자의 읽는 순서다.

## 파일 표시 수준

모든 파일을 읽은 뒤 다음 중 하나를 선택한다.

- `detail`: 독자가 실제 조건, 변환, 효과 또는 문제를 코드로 확인해야 한다.
- `summary`: 변경의 존재와 역할은 알아야 하지만 코드 자체가 새로운 판단을 제공하지 않는다. 화면에서는 핵심 코드 뒤의 닫힌 보조 변경 묶음으로 내려간다.
- `omitted_files`: 다른 source-of-truth에서 파생됐거나, 반복·배선·잠금 결과라 문서에서 제거해도 흐름과 위험 판단이 유지된다.

큰 diff도 상세 파일 3~5개를 먼저 목표로 삼고, 서로 다른 계약의 근거가 더 필요할 때만 늘린다. 파일 수 목표를 맞추려고 중요한 위험 근거를 숨기지 않는다. 테스트도 모두 보여주지 말고 서로 다른 계약을 대표하는 시나리오만 상세로 남긴다. 생략은 미검토가 아니다. 파일을 읽고 영향이 낮다고 판단한 경우에만 생략하며, 읽지 못한 파일은 `unreviewed_file_ids`로 분리한다.

section은 기본적으로 접어 둔다. 제목과 summary는 접힌 상태에서도 보이므로 설명 흐름을 유지할 수 있다. 독자의 첫 화면을 긴 코드로 채우지 않는다. 펼친 상태가 필요한 짧은 결정 지점만 예외로 두고, 관련 없는 반복·배선·오류 메시지는 파일 안에서도 접는다.

## 문장과 제목

독자에게 내부 검토 용어를 떠넘기지 않는다.

- 나쁜 제목: `Notification service 변경`, `Mechanical`, `기타 수정`
- 좋은 제목: `알림을 받을 기기를 어떻게 고르는가`, `앱 버전을 저장할 자리를 추가한다`
- 나쁜 설명: `observed high finding`, `generated로 분류`
- 좋은 설명: `최신 기기 하나를 고르지만 실제 발송에는 회원의 모든 토큰을 넘긴다`

제목은 독자의 질문으로 쓰고 summary는 입력 → 판단 → 결과가 드러나는 2~4문장으로 쓴다. 필요한 배경을 생략해 문장을 줄이지 않는다. 한 문장에 처음 보는 개념을 여러 개 쌓지 않는다. 코드 해설도 `핵심 로직`, `정책`, `연결부`처럼 이름만 붙이지 말고 어떤 약속을 지키기 위해 그 조건이 필요한지 설명한다.

- 낮은 추상화: ‘requestId로 기존 레코드를 조회하고 있으면 early return한다.’
- 높은 추상화: ‘화면에 완료 응답이 도착하지 않았어도 서버에는 이미 저장됐을 수 있습니다. 다시 시도할 때는 앞선 저장 결과를 돌려줘 같은 데이터가 두 번 생기는 일을 막습니다.’
- 뒤따르는 근거 설명: ‘이 분기는 같은 요청의 저장 결과가 있으면 새로 만들지 않고 기존 결과를 반환합니다. 동시 요청에서도 중복을 막는지는 별도 근거로 확인합니다.’

## 먼저 볼 점

`attention`은 독자가 상세 변경보다 먼저 판단할 가치가 있는 항목만 담는다.

- `fix`: 현재 코드에서 재현 가능한 결함이나 깨진 계약
- `caution`: 조건과 영향이 구체적인 회귀·호환성·운영 위험
- `confirm`: 빠진 근거 때문에 결론이 달라질 수 있는 질문

각 항목은 독자가 이해할 수 있는 상황 → 시스템이 하는 일 → 사용자·운영 영향 순서로 쓴다. 상세 section보다 먼저 읽히므로 뒤에 나오는 구현 설명을 전제로 하지 않는다. 제목도 상태명보다 피해나 판단할 질문을 말한다. 예를 들어 ‘중복 검사 분기 누락’보다 ‘저장을 다시 시도하면 같은 데이터가 두 번 생길 수 있다’가 먼저다.

가능하면 작은 실행 순서나 수량 예시로 조건을 설명하고 정확한 분기·행은 evidence로 연결한다. 확인한 사실과 가설·실행 미재현을 구분한다. 취향, 스타일, 막연한 가능성은 넣지 않는다. 해당 사항이 없으면 `먼저 볼 점` 자체를 생략한다.

## 남길 코드와 접을 코드

다음은 설명과 직접 연결되는 근거로 남긴다.

- 바뀐 계약이나 정의
- 동작 여부를 가르는 조건
- 데이터나 상태의 변환
- 반환, 저장, 요청, 이벤트, 오류처럼 관찰 가능한 효과
- 인증, migration, 동시성, 생명주기, 호환성 경계
- 테스트의 구별되는 입력과 결정적인 기대 결과

다음은 전체 내용을 복구할 수 있을 때 파일 내부에서 접는다.

- 조건과 효과가 같은 반복 호출부
- 손으로 쓴 원본 변경이 별도로 확인되는 생성 결과
- 큰 literal, fixture 준비, assertion 반복, snapshot, lockfile
- 의미가 같은 오류 문자열 조립이나 형식 변경
- 새 의미가 없는 import 정렬·추가와 dependency injection 배선

import는 자동으로 잡음이 아니다. 새 의존성, side effect, alias 변경, 새로운 아키텍처 경계를 드러내면 남긴다. 그 외 import 묶음은 `collapse`로 접고 어떤 동작에 쓰는 모듈인지 한 줄로 요약한다. `import 추가`, `dependency injection 주입`, `hook 연결`처럼 구현 행위를 그대로 옮긴 문구는 피한다. 이동 후보는 삭제와 추가를 따로 설명하지 말고 어디로 옮겼으며 주변 동작이 달라졌는지 확인한다.

마이그레이션·테스트·생성물은 보통 관련 흐름의 보조 변경이나 별도 접힌 section에 둔다. 별도 section을 만들 이유는 독립적인 독자 질문이 있을 때뿐이다. 폴더나 파일 종류를 모두 문서 목차로 만들지 않는다. 접힘은 중요하지 않다는 뜻이 아니라 설명을 먼저 읽고 근거를 선택한다는 뜻이다.

## 큰 diff

전체 파일 목록과 전역 힌트를 먼저 읽고, 파일·hunk 경계로 나뉜 모든 chunk를 검사한다. 중복이나 생성 후보는 정적 힌트일 뿐 결론이 아니다. 각 위치의 guard, 데이터 원천, side effect, 호환성 경계, 테스트 결과가 같은지 확인한다.

모든 chunk를 본 뒤 파일을 의미 묶음으로 재배열한다. 한 chunk씩 요약한 결과를 이어 붙이거나 파일 순서대로 section을 만들지 않는다. context 한계 때문에 일부만 읽었다면 미검토 파일을 명시하고 `partial`로 끝낸다.

## 제로 컨텍스트 검수

preview가 VALID여도 아래 의미 검수에 실패하면 설명을 다시 쓴다. 검사 대상은 코드를 가린 문서의 summary·overview·section 제목과 summary·attention이다.

- **배경**: 서비스를 처음 듣는 독자가 누구의 어떤 문제인지 설명할 수 있는가?
- **변화**: 변경 전/후와 이번에 하지 않는 일을 구분할 수 있는가?
- **역할**: 각 시스템과 핵심 대상이 무엇인지, 왜 구분되는지 문서 안에서 알 수 있는가?
- **흐름**: 정상 사례 한 건을 시작부터 결과까지 따라갈 수 있는가?
- **용어**: 아직 설명하지 않은 코드 식별자나 업무 약어가 설명의 핵심을 대신하지 않는가?
- **위험**: 주의점만 먼저 읽어도 발생 조건과 실제 영향을 이해할 수 있는가?
- **증거**: 쉬운 설명을 위해 보장 범위를 부풀리거나 중요한 경계를 지우지 않았는가?

재사용할 평가 상황은 ‘처음 보는 외부 연동 PR’, ‘화면 변화가 없는 저장 방식 변경’, ‘선행 PR 위에 쌓인 후속 변경’이다. 각각에서 위 질문에 답할 수 있어야 한다. 사용자 피드백으로 평가하되 형식 검증 성공을 설명 품질의 증거로 삼지 않는다.

## 근거와 검증

내부 `D...` ID는 원본 줄을 잃지 않기 위한 좌표다. 독자 화면에서는 파일 경로와 실제 old/new 줄 번호를 우선한다. 파란 강조선은 section 설명과 직접 연결된 줄에만 사용하고, 그 이유를 해당 영역 바로 위의 짧은 주석으로 보여준다.

정적 코드 확인, 로컬 테스트·typecheck·lint·build, 원격 CI, merge·배포, 실제 런타임 관측을 구분한다. 실제로 확인한 것만 기록한다. diff에 테스트 파일이 있다는 사실은 테스트 통과가 아니다.

검증 근거는 대상 코드에 관한 사실만 독자에게 보여준다. Easy Review가 모든 chunk를 열었다는 기록, 원본 hash와 계획 schema 확인, 근거 ID 유효성, coverage 계산, 렌더링 성공은 결과물의 내부 무결성 조건이지 대상 코드의 품질 근거가 아니다. 이런 자체 점검은 `verification`에 넣지 않고 실패하면 결과 생성을 중단한다.
